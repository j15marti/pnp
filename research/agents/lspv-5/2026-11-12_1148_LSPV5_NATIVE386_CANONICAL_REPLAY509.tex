\section{Claim card and falsifiers}
\paragraph{Target claim.}
Let $C_{386}(b)$ be the exit-status acceptance predicate of the complete
archived /386 command-line checker on byte string $b$, and define
\[
  \kappa(b)=\operatorname{UTF8}\bigl(
       \operatorname{JSON.stringify}(\operatorname{JSON.parse}(b))
       \mathbin{\|}\texttt{``\textbackslash n''}\bigr).
\]
For every accepted /386 packet $b$, test and prove whether
$C_{386}(\kappa(b))$ also accepts with the same logical work.  The quantifier
is over the accepted language of one pinned program, not over a proposed
completion and not over all historical operations.

\paragraph{Precise falsifiers fixed before search.}
The claim would fail if (F1) the checker consulted a raw substring, byte
length, or source hash before acceptance; (F2) reserialization changed a live
negative zero, rounded number, duplicate member, or property order and flipped
the verdict; (F3) a bundled hostile-control mutation depended on serialization
detail not present in the core; or (F4) a cheap canonical abstract path failed
concrete replay.  None occurred.  The raw-input SHA in successful diagnostic
output does change; that is an output-equivalence falsifier and is stated as a
scope boundary rather than hidden.

\section{Pinned authority and theorem}
The sole acceptance oracle is
\path{experiments/arc/lspv2_386_independent_verify.js}, Git blob
\texttt{338305c0ce101704205e57543756b8127074a986}, SHA-256
\texttt{22d12f665fecede1a047ea20c0c2d3f245c7195ce5df44f342891198ea04a113}.
It reads bytes, calls Node's \texttt{JSON.parse}, checks signed SOURCE,
conservative paid AND2 owners and free DEF facets, and strict oriented binary
Resolution, then runs eleven negative mutations for every successful input.
No inference rule was edited or reimplemented.

\paragraph{Theorem 509.1 (accepted-language reserialization closure).}
For every byte string $b$ for which the pinned complete /386 CLI accepts,
the same CLI accepts $\kappa(b)$ with the same parsed SOURCE count, DEF-view
count, Resolution count, record count and paid total.  The parsed completed
refutation is preserved.  The successful diagnostic SHA is generally
different, so the theorem is not raw-output equality and does not assert that
the byte strings are identical.

\paragraph{Proof.}
Inspect the pinned program.  Before its success decision, the only use of the
file is \texttt{JSON.parse(content)}.  The mathematical checker and all eleven
mutations consume the resulting object; the raw buffer is used only after
success to print a SHA-256 diagnostic.  Arrays retain order under parse and
stringify.  Every object field used by the checker is accessed by name, never
by property enumeration order.  Duplicate names have already been resolved by
\texttt{JSON.parse}; reserialization retains the resulting value.

It remains to audit numeric exceptional cases.  Every checker-read clause
literal and gate tuple member is required to be a safe integer; every parent,
pivot, graph endpoint, height and guard is checked as an integer with its
relevant bounds, and charges are restricted to zero or one.  A non-finite
number in any such live position cannot occur in an accepted packet.  A
negative zero may survive parsing, but in every accepted position the program
uses integer predicates, ordinary equality, array indexing, string conversion,
or ECMAScript Map/Set keying, all of which give the same checker observation as
positive zero; positions that require a nonzero literal or pivot reject both.
Any non-finite value in an unchecked extension field may stringify to null,
but no checker transition observes that field.  Strings, booleans, nulls and
finite numbers otherwise round-trip to values with the same checker
observations.  Thus parsing $\kappa(b)$ yields an object observationally
equivalent at every read performed by the core and bundled controls.  The
control-flow decisions, completed empty-clause sink, counters and paid sum are
identical.  Therefore acceptance and the listed costs agree. \(\square\)

\paragraph{Terminology guard.}
This $\kappa$ is the checker-specific ECMAScript reserialization used by the
experiment.  It is not RFC 8785 JCS: it does not recursively sort object names
or impose I-JSON.  RFC 8259 warns that duplicate object names reduce
interoperability; ECMA-262 specifies that earlier duplicate values are
overwritten; RFC 8785 supplies a stronger canonical representation.  Those
sources explain the representation boundary but do not prove this
program-specific theorem.
