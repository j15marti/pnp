## Theorem 546.1: leading BOM is not native JSON whitespace

Let `b` be any raw file that begins with the exact three bytes `EF BB BF`. In Node's Buffer/UTF-8 replacement decoder `D_N`, those bytes become an initial U+FEFF. The unmodified historical checker evaluates `JSON.parse(D_N(b))`. Since ECMAScript JSON whitespace consists of tab, CR, LF and U+0020, not U+FEFF, the parser throws before any proof inference runs. Thus **every** such raw file is excluded from this recovered checker's accepted-byte language.

In contrast, the default WHATWG `TextDecoder('utf-8')` removes the initial BOM. If `b_0` is an accepted original K4 certificate and `b = EF BB BF || b_0`, the default decoder maps `b` to the same proof JSON text as `b_0`. Therefore the candidate abstraction that uses the default decoder and the original proof checker admits an **abstract accepting path** that is not a concrete native accepting path.

The refinement `R_{BOM}` records whether raw offset zero starts with `EF BB BF`, retains that fact through decoding, and excludes the BOM-prefixed class from the **recovered checker** transition relation. This exclusion is sound because every native-accepted certificate lacks that prefix. A conservative byte decoder must still represent invalid UTF-8 sources accepted by native replacement decoding, as demonstrated by LSPV-2/545. This is a CEGAR repair of a specific spurious path, not a discovery of missing full-rule grammar.

**Cost polarity.** The coarse abstract path's 15 charged paid nodes are no greater than its hypothetical concrete witness cost (none exists for the BOM-prefixed raw file); it cannot be used to prove nonreachability until refined. The refined prefix predicate can be checked in constant auxiliary work and O(1) additional state after fetching three bytes. These are parser precheck overheads, **not** a bound on total verification time, physical peak memory or proof acquisition. There is no general space lower bound here.
