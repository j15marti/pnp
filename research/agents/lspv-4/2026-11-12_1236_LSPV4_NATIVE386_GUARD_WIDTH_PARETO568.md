Define `p_j` as the sum of canonical signed JSON parent-clause lengths **per execution**, including SOURCE/DEF parent reads each time. Let a configuration be a set `M` of at most four currently resident paid RES identities. A RES step `j` is legal only if each paid parent is present. Before execution, any other resident node may be dropped. The result may be allocated fresh if a free register exists, or overwrite one paid parent being discarded if the parent's serialized clause occupies at least `s_j` bytes. Deletion is free; every repeat execution of a paid RES is charged again. Both branches and shared parents are resident physical **one time per identity**, and the original paid definition-owner bank is charged exactly three units globally.

Of the 35 paid RES conclusions, the first 34 contain exactly one signed guard token; the final clause is empty. Hence, relative to `guard=7`, the 16-decimal-digit identifier increases the first 34 canonical signed clause lengths by 15 bytes and leaves the terminal empty-clause length equal to two bytes. Every original RES application `j=0..6` scans one guard occurrence in its parent records; each `j=7..34` scans two. For a schedule executing paid RES identities in order `j_1,...,j_t` (including repeats),

```text
derived_clause_payload(j) = original_size(j) + 15*(j < 34)
parent_scan(j)           = original_scan(j) + 15*(1 if j < 7 else 2)
paid_work                = t + 3
scan_total               = sum over EACH EXECUTION of parent_scan(j)
retention                = sum over SAME TRACE of payload(post_step_mask)
```

Thus W38's parent scan rises from **790 to 1,735** bytes, and the one-recomputation W39 witnesses' scan rises from **809 to 1,769**. These are *per-use source-and-parent canonical-clause read proxies*, not measured CPU load, actual reference-index parsing, or machine cache misses. Scanning a shared parent is charged per use; logically deriving the parent is paid once unless recomputed.
